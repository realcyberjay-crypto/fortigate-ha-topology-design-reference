FoundationsCONCEPT

Six ways to give an HA pair more than one ISP

Every design here uses the same active-passive FGCP cluster (FGT-A primary, FGT-B secondary). What changes is how the ISP hand-offs reach both units, and what you lose when a box fails.

HA is the spare driver. SD-WAN is the GPS. If the driver faints, the spare takes the wheel. If a road closes, the GPS reroutes. You never want a closed road to make the drivers swap seats.

FoundationsCONCEPT

HA and SD-WAN: two jobs, kept apart

FGCP HA answers "which box forwards?". It reacts to a dead unit, a failed heartbeat, or a monitored interface that is down on the primary but up on the secondary.

SD-WAN answers "which ISP carries this session?". It reacts to health-check probes and SLA thresholds on each member, on whichever unit is primary.

The design goal is that an ISP problem never causes an HA failover, and a box problem never needs SD-WAN to notice. That is why the ISP-facing ports are monitored only where a single cable can fail on one unit, and never where both units share the same fate.

Do not use HA pingserver-monitor-interface to chase ISP failures when SD-WAN is in place. Both units reach the internet through the same ISPs, so the "healthier" unit is usually no healthier, and you trade a clean SD-WAN reroute for a full cluster failover.

FoundationsHOW IT WORKS

FGCP failover, step by step

Three settings decide how this feels in production:

  • session-pickup enable syncs TCP sessions; add session-pickup-connectionless enable for UDP and ICMP. Without them every session resets on failover.
  • override disable (default) means the unit with the longest uptime stays primary, so a repaired FGT-A does not grab the role back and cause a second outage.
  • set monitor lists interfaces whose failure on the primary should trigger failover. Monitor an aggregate as a whole, never its members.

Virtual MACs: how two boxes share one IP

Every cluster interface is configured once, on the primary, and syncs. Both units therefore hold the same IP on port1 (203.0.113.2). There is no conflict because the IP is answered with a virtual MAC that belongs to the cluster, not to either box.

  • The primary answers ARP and forwards traffic using the virtual MACs.
  • The secondary keeps its physical MACs and stays silent on the data ports.
  • Every interface gets its own virtual MAC, not every ISP: port1, port2 and port5 each have one.

The prefix 00:09:0f:09 is fixed for FGCP, 0a is the group ID (10) in hex, and the last byte is derived from the interface index. The diagram abbreviates them as …:01 and …:02; read the real values from the unit:

ISP1 diesSD-WANTraffic moves from port1 to port2 on the same box. No MAC moves.

The virtual MAC is a desk phone number that belongs to the office, not to the person. Whoever sits at the desk answers it. When the primary leaves, the secondary sits down and the number keeps ringing; callers never need a new number.

Because the MAC for 203.0.113.2 never changes, the ISP router's ARP entry stays valid through a failover. Only the switch port behind the MAC changes, which the gratuitous ARPs fix. This is also why the group ID must be unique per L2 domain: two clusters with group-id 10 on one switch would generate identical virtual MACs.

FoundationsHOW IT WORKS

SD-WAN health checks and SLA steering

Every design uses the same health check and rule: probes to 1.1.1.1 and 8.8.8.8 over every member, an SLA of 150 ms latency, 30 ms jitter and 2 percent loss, and a Lowest Cost (SLA) rule (mode sla) listing ISP1 before ISP2. Design 6 adds a Best Quality rule (mode priority) for voice.

The static default route points at the SD-WAN zone (set sdwan-zone "WAN", FortiOS 7.0.1 and later). The routing table therefore shows two equal defaults; SD-WAN rules, not the RIB, pick the member.

An ISP switch changes your public source IP. With nat enable, sessions over ISP2 leave as 198.51.100.2 instead of 203.0.113.2, so existing sessions (VPNs, long downloads) reconnect, and inbound services published on ISP1 addresses stay unreachable until ISP1 returns unless you also publish them on ISP2.

FoundationsHOW IT WORKS

LACP to an MCLAG pair: one LAG per FortiGate

Designs 4, 5 and 6 aggregate links. The switch pair presents one logical switch through MCLAG, but each FortiGate still gets its own LAG on it. By default lacp-ha-secondary is enabled, so the standby unit keeps its LAG negotiated and can forward the moment it becomes primary.

If both FortiGates are placed in one switch LAG, the switch mixes active and standby members. If separate LAGs are impossible, the fallback is set lacp-ha-secondary disable, which makes failover wait for LACP to renegotiate.

D1 · Dedicated WAN switchesRUNBOOK

Build order

  1. Stage both units on the same FortiOS build and licence. Factory-reset FGT-B.
  2. Cable only C7, C8, C11 and C12 (heartbeats and management). Leave WAN and LAN unplugged.
  3. Apply the HA block on FGT-A, then on FGT-B. Wait for get system ha status to show both in-sync.
  4. Build WAN-SW1 and WAN-SW2 (VLAN 101 and 102, STP off on every port).
  5. Cable C1 to C6 and C9, C10.
  6. Paste the cluster config on the primary only. It syncs to FGT-B.
  7. Verify with the commands below, then run the fail-test plan.

Fail-test plan and gotchas

TestExpected resultImpact
Pull C1 (ISP1 CPE)SLA on member 1 fails; new sessions use port2 and its own vMAC; no MAC moves, no HA eventSessions reconnect with public IP 198.51.100.2
Power off WAN-SW1Both units lose port1 equally, so no HA event; SD-WAN uses ISP2Same as ISP1 loss
Pull C3 only (FGT-A port1)Monitored port down on the primary only, so FGT-B takes overSeconds
Power off FGT-AFGT-B becomes primary, takes over every vMAC and sends gratuitous ARPs; synced TCP sessions survive1 to 3 s typical
execute ha failover set 1Clean, reversible failover for a change windowSeconds

set monitor only fails over when the primary loses a link the secondary still has. A dead WAN switch drops both units equally, so SD-WAN handles it, which is what you want.

The ISP's ARP entry for the cluster IP never changes on failover, because the virtual MAC moves with the primary. What can bite is MAC learning upstream: a CPE with a built-in switch, or a carrier port with MAC limits or port security, may be slow to relearn the MAC on its new path. FGCP sends gratuitous ARPs to force that; if relearning still lags, raise set arps and set arps-interval under config system ha, and ask the carrier whether port security is enabled on the hand-off.

Give each FortiGate its own LAG on the switches (trunk "FGT-A" and trunk "FGT-B"). With the default lacp-ha-secondary enable, a single LAG spanning both units mixes active and standby members. Every VLAN on a FortiLink-managed switch is automatically trunked back over the FortiLink. If you also cable an ISP VLAN port to a physical FortiGate WAN port, the CPE ARP replies go to the FortiLink instead and the WAN appears dead. Put the WAN IP on the FortiLink VLAN interface and nowhere else.

FortiLink is now the WAN path too. A FortiLink or switch-controller problem is a full outage.

User frames cross each FortiLink twice (in and back out), so size the aggregate for double the internet throughput.

Load Sharing · all designsCONCEPT

Active-active ISPs: using both links at once

Every design in this reference can run its ISPs active-active instead of primary-and-backup. Nothing changes in the cabling, the HA block or the switches: load sharing is purely an SD-WAN rule on the primary, so it works the same in D1 to D6.

Two checkout lanes open instead of one. Each customer is sent to a lane and stays in it until they leave. If one lane closes, everyone queues at the other; when it reopens, new customers are split again, but nobody is moved mid-checkout.

  • Per session, not per packet. One download never exceeds one link; the gain is across many users and sessions.
  • Failure is automatic. A member that fails its health check, or its SLA in an SLA-based rule, is excluded, so all traffic uses the survivor.
  • HA is unaffected. Rules sync to FGT-B; after a unit failover the same rule keeps sharing across both ISPs.

Choosing the hash, and what changes for users

hash-mode (SD-WAN rule)BehaviorWatch out
round-robin (default)Each new session goes to the next memberOne user appears from two public IPs: banking, SaaS and some VPNs may log them out
source-ip-basedAll sessions from a user use the same memberUneven if a few heavy users hash to the same ISP

inbandwidth / outbandwidth / bibandwidthMember with most available bandwidthNeeds estimated bandwidth set on each interface

Each ISP has its own public IP. With source NAT, users on ISP1 appear as 203.0.113.2 and users on ISP2 as 198.51.100.2. Allow-lists at partners, SaaS tenants and remote VPN peers must include both addresses.

Load sharing covers outbound sessions. Inbound services (VIPs) still arrive on the ISP whose address the client resolved; publish them on both ISPs, with DNS pointing at both, if inbound should survive an ISP outage.

Sessions opened over ISP2 during an ISP1 outage stay on ISP2 after recovery. Only new sessions rebalance, so the split evens out as old sessions close.

Field ReferenceDECISION

Choosing a design

  1. Must a single FortiGate loss keep both ISPs? If yes, rule out D2 and D3.
  2. Must a single NIC, SFP or cable on the primary avoid an HA failover? If yes, use aggregates: D4, D5 or D6.
  3. Are the LAN fabric and the internet edge run by different teams? If yes, keep ISPs off FortiLink: avoid D5.
  4. Is there a metered or slow backup link? Give it a cost and put it last in every SLA rule, as in D6.
